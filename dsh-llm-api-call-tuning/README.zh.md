# `dsh-llm-api-call-tuning`

[English](README.md) | 中文

一个 DSH 插件，用**一个**设置页统一管理**每个已激活模型提供方路由**的模型请求重试策略。DSH 为每个路由解析一份重试策略——重试模式、最大重试次数、可重试错误码，以及带抖动的有界指数退避（`packages/llm/llm/src/retry-policy.ts`）——但每份策略归提供方自己所有（`llm-deepseek` 与 `llm-deepseek-account` 在 `retryPolicy` 下，`llm-pi-ai` 在 `providers.<id>.retryPolicy` 下），而 DSH 没有全局设置命名空间、命令行开关、环境变量或 GUI 核心页面。手工调整意味着逐行修改每个提供方行，并让五个数值保持一致。

页面分为**两层**：

- **全局设置卡片（最前）**——一张卡片以两个带标题的子分组容纳全部全局开关：
  - **重试**——六个重试值保存在本插件自己的设置命名空间（`llm-api-call-tuning`）中，作为**预设**。保存它们**不会改动任何提供方**。
  - **抓取超时**——两个进程级 HTTP 计时器 `headersTimeoutMs` 与 `bodyTimeoutMs`，由宿主应用到所有提供方路由、联网搜索与 HTTP MCP 服务器共用的 fetch 调度器上。两者默认都是 `unset`，因此全新安装不改变任何行为；`0` 表示显式禁用该计时器，正整数表示以毫秒为单位的时长。
  一个**保存全局设置**会把六个重试叶子与两个抓取叶子放在同一次写入中；**恢复系统默认**只清除两个抓取计时器。
- **各路由覆盖（其下）**——一个路由区：列表上方是原生**路由选择器**，然后每个**偏离**的提供方路由一张**合并卡片**，卡片以两个子分组（**重试策略** / **超时**）同时容纳该路由的重试策略与应用层超时。重试与超时不再是独立区块。路由满足以下条件之一时出现：其**生效的已存重试策略至少有一个叶子**与全局重试值不同，或该路由**显式存有任一超时叶子**；与全局值相同的已存条目会被隐藏。路由卡片通过**叶子路径操作直接写入该提供方自己的设置命名空间**，并且在你编辑字段之前不会写入任何内容。

列表规则刻意不对称：重试是否偏离按**值**比较（与全局重试值比较），超时是否偏离按**存在性**判断，因为全局抓取计时器是 undici 的**传输层**计时器，而路由的 `streamIdleTimeoutMs` / `timeoutMs` / `filesApiTimeoutMs` 是应用层**看门狗**——它们是不同的开关，没有可比较的全局对应值。这些实体是**提供方路由，绝不是模型**：DSH 按路由解析一次重试与超时策略。

提供方路由是权威来源；只有在明确要求时（某张路由卡片上的**使用默认值**，或**应用默认值到全部启用的提供方**）才会复制全局重试值。两个抓取计时器则是独立的**进程级**副作用：它们不属于重试预设，也不会被复制到任何提供方路由。线格式冻结在 [CONTRACT.md](CONTRACT.md)。

## 安装

本插件是 profile bundle，不是 workspace 包。请从 DSH 检出版本安装（以便 `pnpm dsh` 入口可用），把 `link:` 指向本 bundle 目录——路径请换成你自己的检出与插件工作区：

```sh
cd /abs/path/to/deepseek-harness
plugins=/abs/path/to/deepseek-harness-plugins
pnpm dsh plugin --profile web add link:"$plugins/dsh-llm-api-call-tuning"
```

或者，在插件工作区（本 bundle 的父目录）中且 `dsh` CLI 在 `PATH` 上时：

```sh
dsh plugin --profile web add link:"$PWD/dsh-llm-api-call-tuning"
```

在运行中的 GUI 会话中，同一步骤也可以用 `plugin_manager` 工具完成，动作为 `install_bundle`，`target` 填绝对目录路径：

```js
plugin_manager({ action: "install_bundle", target: "/abs/path/to/deepseek-harness-plugins/dsh-llm-api-call-tuning" })
```

返回 `application: "applied"` 表示 profile 已变更。随后请**刷新页面**；首次安装可能还需要重启后端，才能读到 bundle patch。本 bundle 不携带依赖（加载时使用 Host 自己的 `@deepseek-ai/schemastery`），并且没有发布到任何 npm registry：从本检出目录、绝对路径或 `npm pack` 安装是受支持的方式。

## 使用

打开**设置**（侧边栏底部的账户菜单），选择**LLM API 调用调优**，它是导航的最后一行（section order 45）。页面恰有两层：

1. **全局设置**——最前的一张卡片，两个带标题的子分组与一个**保存全局设置**：
   - **重试**——下表六个重试字段各一个控件。这些值存储在 `llm-api-call-tuning` 中，只是**预设**：保存不会改动任何提供方。
   - **抓取超时**——两个进程级 HTTP 计时器，以及**恢复系统默认**。
   卡片还带有**应用默认值到全部启用的提供方**。
2. **各路由覆盖**——列表上方是原生**路由选择器**与**添加**按钮，然后每个偏离路由一张**合并卡片**。卡片包含**重试策略**与**超时**两个子分组、一个**保存**、一个**重置**，以及**使用默认值**（重试部分）。只列出偏离的路由；选择器提供其余路由，并排除已列出的路由。选中一个路由会在本地按生效值生成卡片，**在你编辑字段并保存之前不会写入任何内容**。把某个重试叶子改回全局值（或清空某个超时）会移除该覆盖，因此一旦路由不再偏离，卡片就会消失。列表为空时显示“没有提供方路由偏离全局设置。”；选择器没有可选路由时显示“所有可编辑的路由都已列出。”。

路由满足以下条件之一时被列出：其**生效的已存重试策略至少有一个叶子**与全局重试值不同，或该路由**存有任一超时叶子**。两半刻意不对称：全局抓取计时器是 undici 传输层计时器，而路由的 `streamIdleTimeoutMs` / `timeoutMs` / `filesApiTimeoutMs` 是应用层看门狗，因此没有可与路由超时比较的全局值——存在性是唯一有意义的判断。因此，存有等于包默认值的超时的路由仍会被列出。

已声明但未激活的路由、未声明设置命名空间的路由，以及本部署不提供其命名空间的路由**不会被列出，也无法选择**：没有生效的配置表单就无法证明其偏离，而写入超时叶子会生成不完整的提供方配置，并可能激活未激活的路由。

重试字段表（与 Host `Config` 及上游重试解析器使用的值一致）适用于全局卡片的**重试**子分组与每张路由卡片；后面是两个进程级抓取字段：

| 字段 | 含义 | 接受范围 | 代码默认值 |
| --- | --- | --- | --- |
| `mode` | 重试模式。`normal` 仅在重试上限内重试所选错误码；`always` 对每次失败都重试，直到成功、取消或关闭，并忽略重试上限与错误码列表。 | `'normal'` 或 `'always'` | `'normal'` |
| `maxRetries` | `normal` 模式下首次请求之后的可重试次数；`0` 表示禁用重试。 | 0..9007199254740991 的整数 | `5` |
| `initialDelayMs` | 本地调度的首次重试延迟，单位毫秒。 | 大于 0 的有限数，最大 2147483647；不得大于 maxDelayMs | `500` |
| `maxDelayMs` | 本地调度或接受的提供方延迟上限，单位毫秒。 | 大于 0 的有限数，最大 2147483647；不得小于 initialDelayMs | `10000` |
| `jitterRatio` | 每个本地延迟周围的对称随机倍数：`0` 关闭抖动，`1` 最多翻倍。 | 0 到 1 之间的数 | `0.1` |
| `retryableCodes` | `normal` 模式会重试的稳定临时错误码。 | 来自五个上游错误码的非空且不重复的数组 | `'EMPTY_RESPONSE', 'RATE_LIMIT', 'SERVER', 'TIMEOUT', 'TRANSPORT'` |
| `headersTimeoutMs` | 进程级 HTTP 响应头超时，单位毫秒，由宿主应用到所有提供方、联网搜索与 HTTP MCP 服务器共用的 fetch 调度器上。 | `unset`（保持系统/DSH 默认不变），或 0..2147483647 的整数；`0` 表示禁用该计时器 | `unset`（未设置） |
| `bodyTimeoutMs` | 同一 fetch 调度器上的进程级 HTTP 响应正文（分块）超时，单位毫秒。 | `unset`（保持系统/DSH 默认不变），或 0..2147483647 的整数；`0` 表示禁用该计时器 | `unset`（未设置） |

重试行的**代码默认值**列是上游解析回退值（`retry-policy.ts:14-22`），也是未配置的提供方路由实际运行的值。bundle 不写入任何初始值，因此页面从这些值开始。两个抓取行的代码默认值是 **`unset`**，而不是数字：schema 刻意没有 `.default()`，所以全新安装不会物化任何计时器，宿主自己的调度器默认值继续生效。`unset` 表示不改变行为；`0` 是真实取值，表示禁用该计时器；正整数表示设置该值。

### 保存全局卡片

**保存全局设置**会先在本地校验六个重试字段与两个抓取计时器（重试规则见下节**保存路由卡片**），然后按一个 revision 围栏提交**一次原子操作列表**：六个重试 `set` 叶子，随后是两个抓取叶子——留空字段发出 `unset`，输入值（包括 `0`）发出 `set`。不会向任何提供方投射：重试值是预设，抓取叶子是进程级副作用。**恢复系统默认**只清除两个抓取叶子，使宿主的系统默认值重新生效；六个重试默认值保留其存储值。

### 保存路由卡片

**保存**会先在本地校验两份草稿——小数重试上限、`0` 或大于 `2147483647` 的延迟、初始延迟大于最大延迟、超出 `[0, 1]` 的抖动、为空/未知/重复的错误码列表，或超出留空/`1..2147483647` 的超时，都会以本地化消息拒绝，且**不发起 Host 调用**——然后按一个 revision 围栏提交**一次原子写入的叶子操作**，同时携带该路由的重试叶子与变更的超时叶子。

重试部分**相对于全局重试值**写入：与全局值不同的叶子写入 `set`；改回全局值的叶子写入 `unset`（仅当用户层确实存有该叶子）；已存且等于全局值的叶子也会用 `unset` 清理。当重试部分的列表非空且其中每个操作都是 `unset` 时，页面把它折叠为单条 `unset [...settingsPath, 'retryPolicy']`。`normal` 模式下涉及 `retryPolicy.mode`、`retryPolicy.maxRetries`、`retryPolicy.retryableCodes` 与三个 `retryPolicy.backoff.*` 叶子；`always` 模式保存会设置 `retryPolicy.mode`，并**清除** `retryPolicy.maxRetries` 与 `retryPolicy.retryableCodes`，因为这两项在上游模式下不生效。永远不会整体*设置* `retryPolicy` 对象，因此同级配置（base URL、凭据引用、模型）不受影响。

超时部分只写入草稿发生变化的叶子：从已存值播种后清空的字段发出 `unset`，输入值发出 `set`，未改动的字段不发出任何操作。刚选中、尚未存有任何内容的路由卡片没有可保存内容（其**保存**保持禁用）；任一份草稿无效或没有任何变化时，**保存**同样禁用。

**重置**用一次写入移除该卡片为该路由存储的全部内容：整个 `retryPolicy` 加本族的超时叶子。对于刚选中、尚未存储覆盖的卡片，**重置**只在本地关闭卡片，**完全不写入**。**使用默认值**把已校验的全局重试默认值复制到重试草稿；在**保存**之前不会写入任何内容。

只有路由表单报告 `ready`、不是只读、且带有数字 revision 时才会尝试写入；同一次读取也用作 revision 围栏，因此页面绝不会发送无条件写入。未通过门控的路由保持禁用，并且**应用默认值到全部**会把它**跳过**而不是写入。

如果 Host 拒绝写入，`mutate` 会解析为 `false`——**所有** Host 拒绝都是如此，包括由 home patch 或 `--patch` 覆盖层拥有该行的情况，因为设置表单 API 不暴露具体原因。页面显示**通用拒绝文案**，并用 Host 随后报告的值重新填充所有字段；如果拒绝源于被取代的 revision 且恢复读取已推进 revision，页面会在新 revision 上**重试一次**。页面仍保留独立的“由其他位置管理”文案，用于直接携带 `settings/rejected` 的 `RemoteError`；该分类仅属防御性分支，通过设置表单 API 不可达：由 home patch 拥有的行显示通用文案。

**应用默认值到全部启用的提供方**会把已校验的全局重试默认值逐个写入每个可编辑路由（已激活、带有设置命名空间且有生效表单），每次使用该表单**新读取**的 revision。每次写入前都会重新检查该行：表单仍在加载、只读或缺少数字 revision 的行会被**跳过**（区域级汇总仍会把它报告为 `skipped`）。它**不是事务**：拒绝的提供方保留原策略，已写入的提供方保持写入，逐行结果会说明哪个是哪种情况。它绝不会把超时叶子或两个抓取计时器写入提供方：它们分别是按路由与进程级的设置，不属于重试预设。

### 超时（路由卡片子分组）

每张合并路由卡片的**超时**子分组编辑位于**各提供方自己的**命名空间中的应用层超时，与**重试策略**子分组走同一条跨命名空间写入路径。默认值就是上游包/SDK 的值；留空不写入任何值，路由保持默认。

| 字段 | 适用路由 | 命名空间 / 路径 | 默认值 | 接受范围 |
| --- | --- | --- | --- | --- |
| `streamIdleTimeoutMs` | 所有已激活路由 | `llm-pi-ai` → `providers.<route>.streamIdleTimeoutMs`；`llm-deepseek` / `llm-deepseek-account` → `streamIdleTimeoutMs` | `300000` 毫秒（5 分钟） | 留空（包默认）或 1..2147483647 的整数；`0` 被拒绝 |
| `timeoutMs` | 仅 `llm-pi-ai` 路由 | `llm-pi-ai` → `providers.<route>.timeoutMs` | 未设置 = SDK 默认（约 `600000` 毫秒） | 留空（SDK 默认）或 1..2147483647 的整数；`0` 被拒绝 |
| `filesApiTimeoutMs` | 仅 `llm-deepseek` 与 `llm-deepseek-account` | `llm-deepseek` / `llm-deepseek-account` 命名空间根 → `filesApiTimeoutMs` | `60000` 毫秒（1 分钟） | 留空（包默认）或 1..2147483647 的整数；`0` 被拒绝 |

为什么拒绝 `0` 而没有关闭开关：DeepSeek 与流空闲 schema 要求严格为正（加载期断言拒绝 `<= 0`），而 SDK 请求超时为 0 会让每个请求立即中止。这些 schema 没有“禁用”状态，因此**不限**预设写入 `2147483647` 毫秒上限（这是上限，不是关闭开关，约 24.8 天）——一个极大的上限，而不是禁用。直接调用 `settings.mutate`（或手工编辑 profile patch）仍可能持久化 `0`；对两个看门狗而言这会触发提供方加载期断言失败，路由随之无法解析——这正是页面要阻止的情况。

与其他两层超时的配合：对 SSE 路由，SDK 请求超时约束的是**等待响应头**的时间，`streamIdleTimeoutMs` 约束的是流式数据块之间的静默时间，进程级抓取 `bodyTimeoutMs` 约束的是传输层数据块之间的时间。当空闲窗口提高到默认 `600000` 毫秒的 SDK 请求超时以上时，若 `timeoutMs` 更短、或抓取正文超时低于空闲窗口，该卡片会给出**非阻断**警告。只提高空闲窗口而让更短的 SDK 或传输期限先触发是无效的。

诊断指引：`llm-pi-ai` 报出 **stream idle timeout after 300000 ms** 时，是默认空闲看门狗中止了慢速首个 token（TTFT 卡顿），不是传输失败。请在路由卡片提高 `streamIdleTimeoutMs`（并在更短时同步提高 `timeoutMs` 与抓取 `bodyTimeoutMs`），而不是手工改 profile patch。

`connectTimeoutMs` **不在范围内**：undici 6/7/8 没有按请求的 connect 超时，只能用脆弱的 agent 重建来实现。传输层连接上限应在上游 `packages/util/http-proxy/src/install.ts`（代理感知调度器安装处）修复，而不是本页面。

### 抓取超时（进程级）

全局卡片的**抓取超时**子分组编辑本插件命名空间顶层的两个叶子。三态契约如下：

- **空输入 = `unset`**——全新安装状态。保存空字段会发出 `{ op: 'unset', path: ['<key>'] }`，因此不应用本插件的任何计时器，宿主/系统默认值保持不变。全新安装不改变任何行为。
- **`0` = 禁用**——真实的写入（`{ op: 'set', path: ['<key>'], value: 0 }`），在视觉上与空输入不同，表示“禁用该计时器”，而不是“未设置”。
- **正整数 = 自定义毫秒数**，最大 `2147483647`。

该效果是**进程级**的：宿主包装当前全局 undici 调度器，只在请求自身未设置 `headersTimeout`/`bodyTimeout` 时填入这两个值，因此进程内所有提供方路由、联网搜索与 HTTP MCP 服务器共享它。请求自带的超时始终优先。包装仅在两个值中至少一个为数字时惰性安装；清除最后一个值会恢复宿主原有调度器（且仅当该包装仍是当前调度器时），之后的实时保存会重新安装。这是一个**过渡方案**：改编自 MIT 许可的 `dsh-fetch-timeouts` 项目（© 2026 Dev Mehra），署名与来源记录在仓库根目录的 [THIRD-PARTY-NOTICES.md](../THIRD-PARTY-NOTICES.md)。它不是 DSH 原生设置，未来的 DSH 版本可能取代它。

### 生效与持久化语义

- 保存走共享设置表单 API——与模型页面相同的 `settings.mutate` 路径——设置服务会把变更持久化到活动 profile 的 `cordis.patch.yml`（profile 自己的 patch，与它的 `package.json` 相邻）。插件自身不存储任何内容。
- 重试策略的变更预期在**下一次模型请求**生效，**无需重启后端**：每条路由的策略在**注册时**捕获（`packages/llm/llm/src/index.ts:435-470`），各提供方在 loader 报告 volatile 值变化（即设置保存之后）时重新注册路由。`llm-deepseek`/`llm-deepseek-account` 在 `llm-deepseek/src/host.ts:82-90` 完成；`llm-pi-ai` 把 `retryPolicy` 纳入注册事实，并在 `loader/volatile-update` 时重新注册（`llm-pi-ai/src/index.ts:108-120,289-319`）。
- 已经在进行中的请求保持其开始时的策略。
- 路由卡片上的超时修改持久化在提供方自己的命名空间中，并在下一次请求/路由注册时生效，无需重启后端；休眠路由或命名空间不可用的路由不会在此列出，因此无法被写入。
- 抓取计时器的修改会在**下一次 HTTP 调度**时生效（包装会在每次请求时重新读取实时值），**无需重启后端**。这些值和其他 Host 设置一样持久化在本插件的设置命名空间中；清空（或重置）后恢复系统默认状态。
- 选中路由不会写入任何内容。只要任一提供方表单快照发生变化（包括来自其他页面的写入），偏离列表与选择器就会重新计算；而提供方**目录**本身每次挂载只读取一次。
- 页面只在安装/升级后需要刷新（首次安装可能还需要重启后端）；修改数值则两者都不需要。

### 两半的职责

`index.js`（Host）拥有全局默认值 `Config`——六个 `.volatile()` 重试字段加两个进程级抓取字段——以及 `DEFAULT_TUNE`/`TUNE_OPTIONS`、`DEFAULT_FETCH`/`FETCH_KEYS`/`FETCH_OPTIONS`、`PROVIDER_TIMEOUT_FIELDS`/`PROVIDER_TIMEOUT_KEYS`/`PROVIDER_TIMEOUT_OPTIONS`（路由卡片的冻结元数据，**不是** `Config` 字段）、`validateTune()`（schema 无法表达的重试组合规则守卫）和 `apply(ctx, config)`。`apply()` 有两项职责：为该命名空间注册文档化的 `auto: false` 页面策略（当前只是面向未来的准备：本版本没有内置客户端会从 schema 生成页面），以及安装上述可选的抓取超时调度器包装。它从不把任何值投射到提供方。`client.js`（浏览器）是页面：一张**全局设置**卡片加一层**各路由覆盖**。它从 Client Remote `llm` 命名空间读取提供方目录，从每个路由自己的配置表单读取生效策略与已存超时叶子，并通过同一表单写回叶子路径操作，且从不持有路由状态的副本。提供方路由是事实来源；`DEFAULT_TUNE` 是页面提供的预设，而不是回退层；抓取计时器是进程级副作用，不是任何提供方的回退。

## 故障排查

- **导航行缺失。** bundle 未加载到活动 profile，或安装后尚未刷新页面。确认安装命令正常结束，做一次完整页面刷新；如果仍缺失，重启后端以重新读取 profile patch。该行应位于设置导航末尾（order 45）。
- **某张路由卡片缺失。** 页面只列出**偏离**的路由：如果某路由的生效重试策略在每个叶子上都等于全局重试值，且没有存储任何超时叶子，它就不会显示。若想为其设置覆盖，请用路由选择器添加它；选中后在你编辑字段之前不会写入任何内容。与全局值相同的已存重试覆盖同样会被隐藏。
- **某路由不在选择器中。** 选择器只提供本部署中已激活、声明了设置命名空间且有生效配置表单的路由。已声明但未激活的 `llm-pi-ai` 路由、没有设置命名空间的路由，以及本部署不提供其命名空间的路由都不会列出，也无法选择：没有生效表单就无法证明其偏离。
- **由 home patch/`--patch` 拥有的行显示“宿主拒绝了本次写入”。** home patch 或 `--patch` 覆盖层拥有该提供方行，配置编辑器拒绝写入，页面显示**通用**拒绝文案（设置表单 API 不暴露原因）。请改为编辑覆盖层（或 profile patch）；本页面刻意不提供强制写入。独立的“由其他位置管理”文案只用于直接携带 `settings/rejected` 的 `RemoteError`，在此不可达。
- **普通行显示“宿主拒绝了本次写入”。** 写入值未被接受（例如 revision 已被取代）。字段会用 Host 当前值重新填充；请检查后再次保存。
- **保存全局卡片后没有变化。** 这是设计如此：重试值是预设。请用某张路由卡片的**使用默认值**或**应用默认值到全部启用的提供方**把它们写入提供方。
- **显示值与输入不一致。** 页面始终显示 Host 报告的生效值。路由卡片处于 `always` 模式时，重试上限和错误码列表不可编辑，并会在保存时被清除；全局卡片仍会保存它们，因为它们是面向所有路由的预设。
- **提供方目录不可用。** 本部署未暴露 Remote `llm` 目录（`providers.unavailable`），或读取失败（`providers.error`）。此时无法列出或选择任何路由，但全局卡片仍可用。
- **刚添加的提供方没有列出。** 目录只在页面挂载时读取一次，不会实时刷新；请离开后重新进入（或刷新页面）以重新读取。
- **`llm-pi-ai` 调用报 stream idle timeout after 300000 ms。** 这是包默认空闲看门狗（慢速首个 token / TTFT 卡顿），不是传输错误。请在路由卡片提高 `streamIdleTimeoutMs`，并在更短时同步提高请求 `timeoutMs` 与进程级抓取 `bodyTimeoutMs`。若仍有更短的期限先触发，该卡片会显示非阻断警告。
- **某张路由卡片是只读的。** 若卡片表单报告加载中、只读或不可用，则不会被写入：写入超时叶子会生成不完整的提供方配置并可能激活休眠路由。这类路由本身也无法被选中，因为候选过滤只提供已激活、已声明命名空间且有生效表单的路由。

## 校验

```sh
DSH_HARNESS_CHECKOUT=/path/to/deepseek-harness node dsh-llm-api-call-tuning/verify.mjs
```

在本仓库根目录运行（或在插件目录内导出同一变量后运行）。套件是封闭的——纯 Node、`node:assert/strict`、`node:vm` 中的 Context/表单/React 替身，无网络、无服务器、无文件写入——并通过 `$DSH_HARNESS_CHECKOUT` 解析**真实的** `@deepseek-ai/schemastery` 与上游 `retry-policy.ts`，因此 schema 或常量漂移会显式失败。它覆盖 manifest 与 bundle patch、Host `Config` 的接受/拒绝矩阵、`validateTune()` 规则、`apply()`、客户端注册（一个 section、id `llm-api-call-tuning`、order 45）、en/zh 文案一致性（120 个键）、渲染出的两层布局（唯一的全局卡片位于各路由区之前；两个子分组都存在；旧的独立重试/超时区块已消失）、仅列出偏离路由的规则（与全局值相同的已存重试覆盖被隐藏、只存有超时的路由会被列出、选择器排除已列出路由、选中后新增一张卡片、空态会渲染）、精确操作形状（全局保存同时携带重试与抓取叶子、合并路由保存与重置、改回全局值的叶子发出 `unset`、全 unset 折叠）、提供方超时元数据（冻结的键/默认值/边界/作用域及其镜像的上游 schema 与默认值）、校验、拒绝、逐写门控/跳过与 revision 重试路径、提供方目录合并与所有降级路径、路由卡片行为（按族显示字段、从用户层播种、协议显示、警告、仅激活门控、不限预设、拒绝 0）、抓取超时调度器对记录型假调度器与宿主真实 `undici` 全局对象的安装/填充/恢复/dispose/`NODE_USE_ENV_PROXY` 行为（含 `undici` 不可解析时的子进程场景），以及本 README 与 CONTRACT.md 中的字段表。“由其他位置管理”分类只作为防御性单元路径用会 reject 的假表单测试；真实设置表单的拒绝会解析为 `false`。

一次绿色运行会对全部检查报告 `0 failed, 0 skipped` 并以 `0` 退出。这是离线契约检查，不是真实 GUI 测试：它不启动 Host 或浏览器，也不会执行真实设置保存、真实导航行、下一请求延迟、一次真实 HTTP 请求在已安装调度器下真正超时的验证，或真实提供方路由因超时中止慢速首个 token 的验证。这些仍属于部署检查；套件证明的是线格式契约与调度器形状，而不是真实计时。

## 限制

完整列表见 [CONTRACT.md](CONTRACT.md)；用户最可能遇到的包括：

- **没有跨提供方事务。** 应用到全部时逐个提供方写入；失败时此前的写入仍然保留。
- **home patch / `--patch` 拥有的行无法编辑**，会显示通用拒绝文案（“由其他位置管理”分类仅是防御性分支，通过设置表单 API 不可达）。
- **进行中的请求保持旧策略。**
- **按路由，而不是按模型。** DSH 在适配器注册时按**提供方路由**捕获一份重试策略（`packages/llm/llm/src/retry-policy.ts:78,450-455`），而 agent/request-error 负载只携带提供方、不携带模型（`packages/core/agent/src/runtime-types.ts:389`）。按模型覆盖会被存储和渲染，但永远不会生效，因此页面不提供该能力。
- **休眠路由、没有设置命名空间的路由，以及命名空间不可用的路由不会被列出，也无法选择。** 没有生效的配置表单就无法证明其偏离，而写入超时叶子会生成不完整的提供方配置并可能激活休眠路由。
- **与全局值相同的已存覆盖会被隐藏。** 列表是偏离列表，而不是存储状态列表：与全局重试值完全相同的 `retryPolicy`（或只存有等于包默认值的超时叶子）不会生成卡片。超时叶子仍按存在性视为偏离，因为没有全局对应值可比较。
- **提供方目录每次挂载只读取一次**，没有实时刷新：页面保持打开时新增或移除的提供方需要刷新页面。
- **不存在命令行、环境变量或 GUI 核心设置**——本页面是唯一受支持的 UI；手工编辑 profile patch 会绕过其校验。
- **提供方超时按路由生效，且拒绝 `0`。** 页面拒绝 `0`，因为 DeepSeek/流空闲 schema 拒绝它，而 SDK 请求超时为 0 会让每个请求立即中止；**不限**预设写入 `2147483647` 毫秒上限（约 24.8 天）而不是关闭开关。直接调用 `settings.mutate` 仍可持久化 `0`，这会触发提供方加载期断言失败并使路由无法解析。
- **超时警告只是启发式，不是强制。** 它在本地比较卡片草稿值与进程级抓取正文超时草稿；通过直接写入或其他命名空间层级设置的更短期限不会被发现，且警告从不阻止保存。
- **`connectTimeoutMs` 不在范围内。** undici 6/7/8 没有按请求的 connect 超时；传输层连接上限应在上游 `packages/util/http-proxy/src/install.ts` 修复，而不是本页面。
- **抓取计时器是进程级的。** 它们作用于 Host 进程内所有提供方路由、联网搜索与 HTTP MCP 服务器；没有按提供方区分的 HTTP 超时。`unset` 保持宿主默认不变，`0` 禁用该计时器，调用方为单次请求设置的超时始终优先。
- **抓取调度器包装是过渡方案**，改编自 MIT 许可的 `dsh-fetch-timeouts` 项目；署名与来源记录在仓库根目录的 [THIRD-PARTY-NOTICES.md](../THIRD-PARTY-NOTICES.md)。它不是 DSH 原生设置。
- **真实计时无法离线证明。** `verify.mjs` 只是用记录型假调度器固定安装/填充/恢复的形状，无法证明真实请求会在配置的毫秒数后超时；那属于部署检查。
- **未发布到 npm**，插件在安装或卸载时不执行任何迁移。
